# SOURCE_AUDIT_20261101 — первинний аудит джерел

Дата перевірки: 2026-11-01. Це документальний аудит публічної документації; live API з ключами не викликались.

## 1. API «Повітряна тривога»
Документація/заявка: https://api.ukrainealarm.com/

Стан: **основний кандидат для офіційного статусу**, доступ не отриманий і runtime не перевірений.
Публічна сторінка описує API як офіційний API для поширення інформації, що надходить у застосунок «Повітряна тривога», і вимагає подати заявку та погодитися з офертою.

До production треба окремо перевірити:
- текст оферти й дозволений спосіб публічної ретрансляції;
- формат/версії endpoint, автентифікацію, rate limits;
- часові мітки, початок/відбій, регіональну ієрархію;
- фактичну затримку, доступність і поведінку при помилках.

## 2. alerts.in.ua
Документація: https://devs.alerts.in.ua/

Стан: **сильний кандидат для додаткового/резервного агрегованого джерела**, але не підміняє офіційне джерело.

З документації на 2026-11-01:
- потрібен персональний API token;
- токен є секретом і не повинен публікуватися;
- для публічних сервісів кінцевий користувач повинен отримувати дані через наш proxy, а не напряму з API;
- soft limit орієнтовно 8–10 запитів/хв з IP; hard limit 12/хв;
- підтримується If-Modified-Since / Last-Modified для кешування;
- можливі 401/403/429 та затримки/тимчасова недоступність;
- сервіс прямо застерігає не використовувати API для критичної інфраструктури;
- v1/v2 endpoints можуть представляти статуси областей/районів/громад; v2 розрізняє рівні R/Y/P/N.

Архітектурний наслідок: API token не може бути в desktop/mobile/web клієнтах. Потрібний контрольований relay/cache.

## Поточне рішення
1. Не вибирати остаточне production-джерело без отримання офіційних умов і тестового доступу.
2. Ввести проектний relay як межу секретів та rate-limit/cache, але поки реалізовувати лише offline контракт/синтетичні тести.
3. Клієнти отримують нормалізований стан без third-party token.
4. Відмова relay/source => stale/unknown; не «відбій».
5. У production бажано мінімум два незалежні шляхи спостереження за доступністю, але їхні дані не вважаються незалежними, якщо походять з одного первинного джерела.

## Не перевірено
Юридичний текст оферти UkraineAlarm, SLA, фактичні latency/availability, конкретні credentials, production-навантаження, умови зберігання історії, придатність для масового публічного сервісу.

## Офіційна оферта UkraineAlarm — перевірено 2026-11-01
Джерело: https://api.ukrainealarm.com/contract.pdf

За чинним опублікованим текстом договору:
- отримання API-ключа після погодженої заявки є акцептом оферти;
- запит може бути HTTP-зверненням або webhook; для webhook Замовник надає адресу свого публічного сервісу;
- Послуга охоплює сповіщення про можливі повітряні, хімічні, техногенні та інші загрози в межах України;
- формат/типи протоколів можуть змінюватись; для несумісних змін передбачене попереднє інформування, але сумісні зміни можуть вводитись без такого строку;
- надання послуг наразі описане як безоплатне;
- Виконавець може відмовити/припинити доступ; API надається «як є» без гарантій точності, своєчасності, безперебійності чи безпомилковості;
- умови оферти можуть змінюватися через публікацію нової версії, а подальше користування означає прийняття нових умов.

Архітектурні наслідки для ТривогА:
1. Не вбудовувати ключ у public clients; заявки/ключі — лише на контрольованому relay.
2. Версіонувати adapter contract і тестувати schema drift.
3. Вважати timeout/access loss окремим станом unavailable/stale, не official clear.
4. Перед production окремо зафіксувати дату й версію оферти, фактичний доступ, endpoint contract, webhook security та правила retention.
5. Наш застосунок не має обіцяти гарантію доставки, якої не гарантує первинний API; UI повинен прямо пояснювати, що він не замінює офіційні канали оповіщення.

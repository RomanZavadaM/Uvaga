# r30 — Першочерговий контур отримання інформації

**Статус: архітектура без live-підключень.** Рішення власника 2026-11-02: пріоритет — максимально оперативне й надійне **приймання** інформації. Сирени, desktop-сповіщення, push і розповсюдження — окремі майбутні етапи.

## Призначення

Збирати дозволені сигнали з якомога ширшого набору незалежних джерел, визначати достовірність, походження, час, вид небезпеки й охоплену адміністративну територію. Не давати неперевіреним агрегаторам змінювати офіційний стан.

## Приймальний тракт

1. **Registry:** реєстр джерел з власником, правами доступу, роллю (офіційне / допоміжне / довідкове), протоколом, схемою, покриттям територій, контактами й обмеженнями. Жодне джерело не отримує офіційний статус автоматично.
2. **Connectors:** окремі адаптери до документованих API, webhook/event stream або контрольованого періодичного опитування. Polling fallback лише за умовами джерела; ключі — виключно на захищеному сервері, не в desktop/mobile застосунку.
3. **Receipt envelope:** source ID, immutable event identity, raw digest, provider-issued timestamp, received timestamp, transport health і schema revision. Сирі дані із секретами або ідентифікаторами користувачів не логувати.
4. **Admission gate:** підтвердження походження, автентичності й дозволу; validation/schema; dedup, ordered replay, rate-limit/backoff, clock-skew checks. Некоректне в карантин.
5. **Normalizer:** вид загрози тільки з достовірно заявленої категорії; географія тільки через перевірену відповідність provider-ID ↔ версійний KATOTTG. Ніяких самостійних траєкторій військових цілей або часу підльоту.
6. **Independent state books:** окремий стан на територію × категорію × компетентне офіційне джерело, із явною політикою вирішення конфліктів. Не перезаписувати актуальні офіційні сигнали непідтвердженими вторинними повідомленнями.
7. **Read-only trusted event journal:** нормалізовані перевірені записи з контрольованим часом і походженням, які зможуть використовувати майбутні desktop/mobile/web клієнти. Доставка користувачам не входить до r30.

## Оперативність і стійкість

- Пріоритет **подійної доставки** (webhook/stream), де її документовано й дозволено; інакше адаптивне опитування з урахуванням лімітів, backoff та повторного підтвердження.
- Мінімум дві фізично/організаційно незалежні точки приймання для критичних джерел — як ціль архітектури, а не вже реалізована функція.
- При відмові каналу автоматично фіксувати stale/unavailable, **ніколи не створювати «відбій»**.
- Після відновлення — повне звіряння стану перед обробкою дельт, уникнення пропуску повідомлень, перевірка монотонності часу.
- Заміряти затримки `issued → received → admitted → normalized` (p50/p95/p99), втрати/дублі/помилки, кількість unmapped territories, schema drift; не обіцяти числовий SLA без замірів.

## Порядок робіт

**r30 (дозволено зараз):** специфікація приймального контуру, каталог джерел без ключів, синтетичні fixture-driven контрактні тести, вимірювання затримок на контрольованих офлайнових даних.

**Наступне (після перевірки r29):** незалежні адаптери форматів, відтворення журналу подій, збої/відновлення, правила конкуренції джерел — без реального доступу.

**Окреме погодження власника:** реальний доступ/оферти/ключі/API, живі запити, експлуатаційний сервер та публічні сповіщення.

## Незалежна робота над r29

PR #65 містить відновлення стану; Rust/relay/docs PASS, але desktop CI має FAIL на кроці відновлення exact dependency lock. **PR #65 не зливати**, доки причину не усунуто та всі повторні перевірки exact-head не пройдено.

Цей документ не змінює r29, product code, версію, релізну політику або source permissions.
